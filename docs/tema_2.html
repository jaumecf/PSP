Bloc 1: Conceptes i Cicle de Vida dels Fils

1.1. Fils (Threads): Què són?

La programació tradicional està dissenyada per treballar de forma seqüencial. Els fils (o threads) permeten executar paral·lelament o concurrentment diferents parts d'un mateix programa dins del context d'un mateix procés.

Un fil és la unitat de processament més petita que pot ser planificada per un sistema operatiu. Els fils són entitats lleugeres perquè tots els fils d'un mateix procés comparteixen l'espai de memòria (variables globals, descriptors de fitxers, heap), la qual cosa fa que la seva creació i canvi de context consumeixin molts menys recursos que la creació de processos independents.

1.2. Relació entre Procés i Fil

  • Processos (Entitats pesades): No comparteixen memòria entre ells. Són independents i la seva comunicació (IPC) requereix mecanismes costosos del sistema operatiu.
  • Fils (Entitats lleugeres): Comparteixen la memòria del procés pare. Si un fil modifica una dada en memòria, la resta de fils tenen accés a la nova dada de forma immediata.
  • Quan un procés s'inicia, es crea com a mínim un fil principal (executat pel mètode main() en Java). Quan el procés finalitza, tots els seus fils finalitzen.
Arquitectura en memòria: Dins d'un procés amb diversos fils, cada fil disposa del seu propi comptador de programa (PC), registre de CPU i la seva pròpia pila d'execució (Stack), però tots comparteixen el mateix espai de dades i codi (Heap).

1.3. Cicle de Vida i Estats d'un Fil en Java

En Java, un fil passa per diferents estats gestionats pel planificador (Thread Scheduler):

  • Nou (New): El fil ha estat instanciat però encara no s'ha cridat al mètode start().
  • Executable / Preparat (Runnable): S'ha executat start(). El fil està a punt per ser executat pel planificador quan li assigni temps de CPU.
  • En Execució (Running): El fil té l'ús de la CPU i executa les instruccions del mètode run().
  • Esperant / Bloquejat (Waiting / Sleeping / Blocked): El fil no està executant-se temporalment per una crida a sleep(), wait(), o en quedar-se bloquejat esperant un recurs sincronitzat.
  • Mort (Dead / Terminated): El fil ha completat totes les instruccions de run() o ha finalitzat per una excepció. No pot tornar a executar-se.

Bloc 2: Creació i Gestió de Fils a Java

2.1. Formes de Creació de Fils

En Java existeixen dues formes principals per definir i executar un fil:

Opció A: Heretant de la classe Thread

Sobreescribim el mètode run() per definir el codi executable del fil.

package heretafil;

public class HeretaFil extends Thread {
    private String strImprimir;

    public HeretaFil(String strP) {
        this.strImprimir = strP;
    }

    @Override
    public void run() {
        for (int x = 0; x < 5; x++) {
            System.out.println(strImprimir + " - passada " + x);
        }
    }

    public static void main(String[] args) {
        Thread primer = new HeretaFil("Fil 1");
        Thread segon = new HeretaFil("Fil 2");

        // Iniciem els fils amb start() (NO cridar directament a run())
        primer.start();
        segon.start();

        System.out.println("Final Fil Principal");
    }
}

Opció B: Implementant la interfície Runnable (Recomanat)

Com que Java no suporta l'herència múltiple, si la nostra classe ja hereta d'una altra entitat, hem d'implementar Runnable.

package runnablefil;

public class RunnableFil implements Runnable {
    private String strImprimir;

    public RunnableFil(String strP) {
        this.strImprimir = strP;
    }

    @Override
    public void run() {
        for (int x = 0; x < 5; x++) {
            System.out.println(strImprimir + " - passada " + x);
        }
    }

    public static void main(String[] args) {
        RunnableFil obj1 = new RunnableFil("Fil 1");
        RunnableFil obj2 = new RunnableFil("Fil 2");

        Thread primer = new Thread(obj1);
        Thread segon = new Thread(obj2);

        primer.start();
        segon.start();

        System.out.println("Final Fil Principal");
    }
}
Atenció (`start` vs `run`): Cridar directament al mètode run() executa el codi de forma seqüencial en el fil actual (main). Per crear un fil independent i paral·lel en el sistema operatiu cal cridar obligatòriament al mètode start().

2.2. Sincronització de la Finalització amb join()

El mètode no estàtic join() permet que un fil d'execució esperi fins que un altre fil hagi completat la seva execució (passant a l'estat Dead). 

try {
    primer.start();
    segon.start();

    // El fil principal (main) s'espera que acabin 'primer' i 'segon'
    primer.join();
    segon.join();
} catch (InterruptedException e) {
    e.printStackTrace();
}

System.out.println("Aquest missatge es mostra quan TOTS els fils han acabat.");

Bloc 3: Mecanismes de Sincronització i Concurrència

3.1. Seccions Crítiques

Una Secció Crítica és el fragment de codi que accedeix a un recurs compartit (variablesglobals, fitxers, bases de dades) i que no ha de ser executat concurrentment per més d'un fil al mateix temps per evitar corrupció de dades o resultats imprevisibles.

3.2. Riscos de la Concurrència

Quan no es gestionen adequadament les seccions crítiques i la sincronització entre fils, el sistema pot patir els següents problemes clàssics:

  • Condició de Carrera (Race Condition): Es produeix quan diversos fils accedeixen simultàniament al mateix recurs compartit i almenys un en modifica l'estat. El resultat final depèn de l'ordre exactament fortuït d'execució assignat pel planificador de CPU.
  • Interbloqueig (Deadlock): Es produeix quan dos o més fils queden bloquejats indefinidament, esperant cadascun un recurs que té reservat l'altre (ex: Fil A té R1 i vol R2; Fil B té R2 i vol R1). Cap fil pot avançar.
  • Inanició (Starvation): Un fil mai no aconsegueix accés al recurs compartit perquè altres fils amb major prioritat o freqüència li treuen el torn sistemàticament.
  • Bloqueig Actiu (Livelock): Els fils canvien contínuament d'estat responent a les accions dels altres fils, però cap d'ells aconsegueix fer cap avanç real en la seva execució (similar a dues persones intentant esquivar-se en un passadís caminant contínuament cap al mateix costat).

3.3. Exclusió Mútua Clàssica amb synchronized

Java permet bloquejar l'accés a les seccions crítiques utilitzant el modificador o bloc synchronized. Quan un fil entra en una secció sincronitzada, adquireix el bloqueig (lock o monitor) de l'objecte de forma exclusiva (1 sol fil a la vegada). 

// 1. Sincronització a nivell de mètode
public synchronized void incrementar() {
    compte++;
}

// 2. Sincronització a nivell de bloc (més granular i eficient)
public void processarDades() {
    // Codi no crític executat en paral·lel
    
    synchronized (this) {
        // Secció crítica: només 1 fil a la vegada
        compte++;
    }
}

3.4. Monitors Natius: wait(), notify() i notifyAll()

Un monitor combina l'exclusió mútua de synchronized amb la coordinació basada en condicions utilitzant mètodes natius de la classe Object.

Com funciona la combinació de `synchronized` i `wait()`?
Quan un fil executa wait(), allibera immediatament el bloqueig (*lock*) del monitor i queda pausat. Això permet que un altre fil pugui entrar al bloc `synchronized`, realitzar la seva feina i cridar a notifyAll() per despertar al fil esperant.
  • wait(): Libera el bloqueig del monitor i posa el fil en estat d'espera fins que un altre fil el notifiqui.
  • notify(): Desperta un dels fils que està esperant en la cua del monitor.
  • notifyAll(): Desperta tots els fils que estan esperant en la cua del monitor.

3.5. Bloquejos Explícits: ReentrantLock i Condition

Són l'evolució i alternativa moderna als monitors natius (synchronized i wait()/notify()). Proporcionen un control molt més granular i flexible sobre els bloquejos de la secció crítica.

  • Permeten intentar adquirir el bloqueig sense quedar-se aturat indefinidament amb tryLock().
  • Permeten associar múltiples condicions d'espera (objectes Condition) a un mateix bloqueig, separant per exemple les cues d'espera de productors i consumidors.
import java.util.concurrent.locks.ReentrantLock;
import java.util.concurrent.locks.Condition;

public class Magatzem {
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition noPle = lock.newCondition();
    private final Condition noBuit = lock.newCondition();

    public void guardarDada() throws InterruptedException {
        lock.lock();
        try {
            // Si està ple, esperem específicament a la condició 'noPle'
            noPle.await(); 
            // Accés a la secció crítica...
            noBuit.signal(); // Notifiquem únicament als qui esperen per consumir
        } finally {
            lock.unlock(); // Semper alliberar el lock en un bloc finally!
        }
    }
}

3.6. Semàfors (Semaphore) i el Semàfor Binari / Mutex

A diferència de synchronized o ReentrantLock (que només permeten 1 sol fil a la vegada), un Semàfor manté un conjunt de permisos (permits) per controlar l'accés simultani a un recurs que pot acceptar fins a un nombre màxim d'execucions concurrents.

  • acquire(): Sol·licita un permís. Si n'hi ha de lliures, decrementa el comptador i continua. Si no, es bloqueja.
  • release(): Torna un permís al semàfor, incrementant el comptador i despertant un fil bloquejat.
Concepte Clau: Semàfor Binari o Mutex
Si instanciem un semàfor amb només 1 permís (new Semaphore(1)), aquest funciona exactament com un bloqueig mutu exclusiu (Mutex). Només un fil pot obtenir el permís i la resta s'han d'esperar fins que es cridi a release(). Aquest patró és molt utilitzat per protegir recursos únics sense fer servir blocs `synchronized`. 
import java.util.concurrent.Semaphore;

// Semàfor comptador: permet un màxim de 3 fils simultanis
Semaphore semaforComptador = new Semaphore(3);

// Semàfor binari / Mutex: funciona com un bloqueig exclusiu (1 sol fil)
Semaphore mutex = new Semaphore(1);

try {
    mutex.acquire(); // Demana l'únic permís disponible
    // Secció crítica d'exclusió mútua estricta
} finally {
    mutex.release(); // Torna el permís indispensablement
}

3.7. Variables i Classes Atòmiques

Les classes del paquet java.util.concurrent.atomic (ex: AtomicInteger, AtomicBoolean, AtomicReference) són indispensables per realitzar operacions d'increment, decrements o modificació d'una sola variable de forma atòmica a nivell d'instrucció de hardware/CPU.

Això evita la sobrecarrega (overhead) i el costós canvi de context d'un bloc synchronized o d'un bloqueig explícit. 

import java.util.concurrent.atomic.AtomicInteger;

private AtomicInteger compte = new AtomicInteger(0);

public void incrementar() {
    compte.incrementAndGet(); // Increment atòmic ultra-ràpid sense utilitzar bloquejos
}

Bloc 4: Problemes ClÀssics i les seves Solucions

A la programació concurrent existeixen patrons de problemes teòrics universals. Entendre'ls és fonamental per dissenyar aplicacions robustes i lliures de bloquejos mutus.

4.1. Problema 1: Productor - Consumidor (Resolt amb Monitor)

Un o diversos fils (productors) generen elements i els col·loquen en un magatzem compartit de mida finita. Altres fils (consumidors) agafen elements d'aquest magatzem. 

public class Buffer {
    private final int[] dades;
    private int cap = 0, inici = 0, contador = 0;

    public Buffer(int capacitat) {
        this.dades = new int[capacitat];
    }

    public synchronized void produir(int valor) throws InterruptedException {
        while (contador == dades.length) {
            wait(); // Buffer ple: el productor allibera el monitor i espera
        }
        dades[cap] = valor;
        cap = (cap + 1) % dades.length;
        contador++;
        System.out.println("Produït: " + valor);
        notifyAll(); // Notifica als consumidors
    }

    public synchronized int consumir() throws InterruptedException {
        while (contador == 0) {
            wait(); // Buffer buit: el consumidor allibera el monitor i espera
        }
        int valor = dades[inici];
        inici = (inici + 1) % dades.length;
        contador--;
        System.out.println("Consumit: " + valor);
        notifyAll(); // Notifica als productors
        return valor;
    }
}

4.2. Problema 2: El Pàrquing / Gestió de Places (Resolt amb Semàfors)

Un pàrquing disposa d'un nombre determinat de places de capacitat limitada. Molts cotxes (fils) volen aparcar. Si el pàrquing està ple, els cotxes han d'esperar en una cua. Aquest problema s'adapta directament a l'ús de Semaphore. 

import java.util.concurrent.Semaphore;

public class Parquing {
    private final Semaphore places;

    public Parquing(int totalPlaces) {
        // Inicialitzem el semàfor amb el nombre de places disponibles
        this.places = new Semaphore(totalPlaces, true); // true = cua justa (FIFO)
    }

    public void entrar(int idCotxe) {
        try {
            System.out.println("Cotxe " + idCotxe + " demana entrar al pàrquing.");
            places.acquire(); // Decrementa les places o es bloqueja si n'hi ha 0
            System.out.println("-> Cotxe " + idCotxe + " ha APARCAT.");
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    public void sortir(int idCotxe) {
        System.out.println("<- Cotxe " + idCotxe + " IEX del pàrquing.");
        places.release(); // Incrementa les places lliures i notifica a la cua
    }
}

4.3. Problema 3: Els Filòsofs Comensals (Interbloqueig / Deadlock)

Cinc filòsofs passen la vida pensant i menjant. Per menjar necessiten dues forquilles (la de la seva esquerra i la de la seva dreta). Només hi ha 5 forquilles a la taula.

  • El risc d'Interbloqueig (Deadlock): Si tots els filòsofs agafen simultàniament la forquilla de la seva esquerra, cap podrà agafar la de la dreta. Tots quedaran bloquejats esperant per sempre.
  • La solució: Controlar l'accés a les dues forquilles de manera que només se n'agafin si ambdues estan lliures al mateix temps.
public class TaulaFilosofs {
    private final boolean[] forquillaOcupada;

    public TaulaFilosofs(int numFilosofs) {
        this.forquillaOcupada = new boolean[numFilosofs];
    }

    public synchronized void agafarForquilles(int idFilosof) throws InterruptedException {
        int esquerra = idFilosof;
        int dreta = (idFilosof + 1) % forquillaOcupada.length;

        // Espera fins que ambdues forquilles estiguin lliures alhora
        while (forquillaOcupada[esquerra] || forquillaOcupada[dreta]) {
            wait();
        }

        forquillaOcupada[esquerra] = true;
        forquillaOcupada[dreta] = true;
    }

    public synchronized void deixarForquilles(int idFilosof) {
        int esquerra = idFilosof;
        int dreta = (idFilosof + 1) % forquillaOcupada.length;

        forquillaOcupada[esquerra] = false;
        forquillaOcupada[dreta] = false;
        notifyAll(); // Notifica als filòsofs veïns
    }
}

Bloc 5: Reptes de Reflexió i Aprenentatge Graduals

Aquestes qüestions i petits reptes estan dissenyats per fer-te pensar sobre la naturalesa no determinista dels fils i experimentar amb els problemes reals de la concurrència.

Repte 1 (Nivell Bàsic): El misteri de l'ordre d'execució

Escenari: Crees un programa que llança 10 fils. Cada fil simplement imprimeix el seu número d'identificador (de l'1 al 10) per consola. Executes el programa 5 vegades segides.

Pregunta de reflexió: S'imprimeixen els números sempre en ordre de l'1 al 10? Per què passa això si els has creat en un bucle ordenat? Com ho pots solucionar si necessites que s'executin en ordre estricte?

Veure Explicació / Solució

Explicació: No, l'ordre d'execució mai no està garantit. El planificador de fils del sistema operatiu (Thread Scheduler) assigna els temps de CPU de forma no determinista segons la càrrega del sistema.

Solució: Per garantir que un fil no comenci o continue fins que l'anterior hagi acabat, cal utilitzar el mètode join() de cada fil abans d'iniciar el següent, o bé utilitzar mecanismes de sincronització/monitors.

Repte 2 (Nivell Intermedi): El comptador desquadrat (Race Condition)

Escenari: Dos fils accedeixen a una mateixa variable int compte = 0;. Cada fil executa un bucle 100.000 vegades fent compte++;. En acabar els dos fils, s'imprimeix el valor final de compte.

Pregunta de reflexió: Per què el resultat final quasi mai és 200.000 i va canviant a cada execució? Quines 3 solucions diferents pots aplicar en Java per corregir-ho?

Veure Explicació / Solució

Explicació: L'operació compte++ no és atòmica. Es descodifica en 3 instruccions de CPU: 1) Llegir valor, 2) Incrementar en 1, 3) Escriure resultat. Si un fil interromp l'altre entre la lectura i l'escriptura, es perden increments (Condició de carrera).

Les 3 Solucions possibles:

  1. Utilitzar un mètode o bloc synchronized.
  2. Utilitzar la classe atòmica AtomicInteger i el seu mètode incrementAndGet().
  3. Utilitzar un bloqueig explícit amb ReentrantLock.

Repte 3 (Nivell Avançat): La trampa del Deadlock accidental

Escenari: Tens dos comptes bancaris (A i B) i dos fils fent transferències simultàniament. El Fil 1 transfereix diners de A cap a B. El Fil 2 transfereix diners de B cap a A. Per fer la transferència, cada fil bloqueja primer el compte d'origen i després el compte de destí.

// Fil 1 (A -> B)             // Fil 2 (B -> A)
synchronized(compteA) {       synchronized(compteB) {
    synchronized(compteB) {       synchronized(compteA) {
        // Transferir                 // Transferir
    }                             }
}                             }

Pregunta de reflexió: Com es pot produir un Deadlock complet en aquest codi? Com el pots modificar per evitar-ho sense canviar l'ús de synchronized?

Veure Explicació / Solució

Explicació del Deadlock: Si el Fil 1 agafa el bloqueig de compteA exactament al mateix temps que el Fil 2 agafa el bloqueig de compteB, quan el Fil 1 intenti bloquejar compteB es quedarà esperant al Fil 2, i quan el Fil 2 intenti bloquejar compteA es quedarà esperant al Fil 1. El programa quedarà congelat per sempre.

Solució (Ordre global de recursos): Cal establir un ordre d'adquisició de bloquejos global i consistent. Per exemple, ordenar els comptes per la seva ID abans de bloquejar-los: 

Compte primer = compteA.getId() < compteB.getId() ? compteA : compteB;
Compte segon = compteA.getId() < compteB.getId() ? compteB : compteA;

synchronized(primer) {
    synchronized(segon) {
        // Transferència segura sense possibilitat de Deadlock
    }
}
